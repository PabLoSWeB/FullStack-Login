CHECKLIST - PROJETO DE CADASTRO/LOGIN (Spring Boot + Spring Security + Front)
==============================================================================

Objetivo: relembrar Spring com um projeto simples, sem relacionamentos.
Ordem natural: (A) API de cadastro funcionando SEM seguranca -> (B) Spring Security -> (C) Front.

Em cada passo ha "PERGUNTE-SE": tente responder sozinho antes de codar.
Se travar, me mande o que voce tentou e eu te guio.


------------------------------------------------------------------------------
FASE A - API BASICA (sem Security)
------------------------------------------------------------------------------

1. CRIAR O PROJETO (start.spring.io)
   [ ] Maven, Java (a versao que voce usa), Spring Boot estavel
   [ ] Dependencias: Spring Web, Spring Data JPA, Validation, banco (H2 para
       comecar ou PostgreSQL/MySQL), Lombok (opcional)
   [ ] NAO adicione Spring Security ainda
   [ ] Depois: adicionar springdoc-openapi (Swagger), como no Book Control
   [ ] Configurar application.properties (datasource, ddl-auto, show-sql)
   PERGUNTE-SE: por que deixar o Security para depois? O que acontece com
   TODOS os endpoints no momento em que a dependencia dele entra no pom.xml?

2. ESTRUTURA DE PACOTES (use o mesmo padrao do Book Control)
   Sugestao:
     controller / service / repository / model (ou entity) / dto / exception
   [ ] Criar os pacotes vazios antes de comecar

3. ENTITY (model)  ->  Usuario
   Campos: id, nomeCompleto, cpf, telefone, email
   [ ] @Entity, @Table(name = "usuarios")
   [ ] @Id + @GeneratedValue
   [ ] cpf e email com @Column(unique = true, nullable = false)
   [ ] Guardar CPF e telefone como String (nunca Integer/Long). Por que?
   [ ] Ainda SEM campo de senha (entra na Fase B)
   PERGUNTE-SE: qual a diferenca entre validar na entity e validar no DTO?
   Onde cada uma costuma ser aplicada?

4. REPOSITORY
   [ ] interface UsuarioRepository extends JpaRepository<Usuario, Long>
   [ ] Metodos derivados: existsByCpf, existsByEmail, findByEmail
   PERGUNTE-SE: o Spring cria a implementacao a partir de que? Como o nome
   do metodo vira uma query?

5. DTOs
   [ ] UsuarioRequestDTO (entrada do JSON de cadastro) - pode ser record
   [ ] UsuarioResponseDTO (saida) - sem dados que nao devem vazar
   [ ] Validacoes no Request: @NotBlank (nome), @Email (email),
       @CPF do Hibernate Validator (cpf), @Pattern (telefone)
   [ ] Metodo de conversao (DTO -> Entity e Entity -> DTO), no proprio DTO,
       em um Mapper ou no service - escolha o que voce ja usa
   PERGUNTE-SE: por que nunca receber/devolver a Entity direto no controller?

   Exemplo de JSON de cadastro:
   {
     "nomeCompleto": "Fulano de Tal",
     "cpf": "12345678909",
     "telefone": "31999999999",
     "email": "fulano@email.com"
   }

6. EXCEPTIONS
   [ ] RecursoNaoEncontradoException (-> 404)
   [ ] RegraDeNegocioException ou ConflitoException (-> 409, CPF/email repetido)
   [ ] GlobalExceptionHandler com @RestControllerAdvice
   [ ] Tratar MethodArgumentNotValidException (erros do @Valid -> 400)
   [ ] Padronizar o corpo do erro (timestamp, status, mensagem, campos)
   PERGUNTE-SE: o que o usuario do front vai receber se o CPF ja existir?
   Qual status HTTP representa melhor isso?

7. SERVICE
   [ ] cadastrar(request): normalizar CPF/telefone (so digitos), checar
       duplicidade de cpf e email, salvar, devolver ResponseDTO
   [ ] buscarPorId(id)
   [ ] listar(Pageable) - paginacao, como no Book Control
   [ ] atualizar(id, request)
   [ ] deletar(id)
   [ ] @Service e, nos metodos de escrita, @Transactional
   PERGUNTE-SE: a checagem de duplicidade no service basta? O que garante a
   unicidade de verdade quando duas requisicoes chegam ao mesmo tempo?

8. CONTROLLER
   [ ] @RestController + @RequestMapping("/usuarios")
   [ ] POST   /usuarios        -> 201 Created (+ header Location)
   [ ] GET    /usuarios/{id}   -> 200
   [ ] GET    /usuarios        -> 200 paginado
   [ ] PUT    /usuarios/{id}   -> 200
   [ ] DELETE /usuarios/{id}   -> 204
   [ ] @Valid no @RequestBody
   [ ] Controller so recebe e devolve; regra fica no service
   [ ] Anotacoes do Swagger (@Operation, @ApiResponse) se quiser

9. TESTAR
   [ ] Swagger UI (/swagger-ui.html) e/ou Postman/Insomnia
   [ ] Casos: cadastro valido, CPF invalido, email invalido, CPF duplicado,
       email duplicado, id inexistente
   [ ] (Opcional) teste unitario do service com Mockito e @WebMvcTest do
       controller
   [ ] Commit: "API de cadastro funcionando sem seguranca" (marco antes do Security)

FASE B - SPRING SECURITY
------------------------------------------------------------------------------

10. PRIMEIRO CONTATO
   [ ] Adicionar spring-boot-starter-security
   [ ] Subir a app e observar: todos os endpoints passam a exigir login
   [ ] Ler a senha gerada no console e testar o login padrao
   PERGUNTE-SE: o que e um filtro (Filter Chain) e por onde a requisicao
   passa antes de chegar no seu controller?

11. SENHA
   [ ] Adicionar campo senha na Entity e no Request DTO (NUNCA no Response)
   [ ] Declarar um @Bean PasswordEncoder (BCryptPasswordEncoder)
   [ ] No service de cadastro: codificar a senha antes de salvar
   PERGUNTE-SE: por que hash e nao criptografia? Por que BCrypt e nao SHA-256 puro?

12. CONFIGURAR O SecurityFilterChain
   [ ] Classe @Configuration + @EnableWebSecurity
   [ ] @Bean SecurityFilterChain (estilo atual, com lambda; nao use o
       WebSecurityConfigurerAdapter, que foi removido)
   [ ] Liberar: POST /usuarios (cadastro), Swagger, endpoint de login
   [ ] Exigir autenticacao para o resto
   [ ] Decidir CSRF (desabilitar so se for API stateless com token)

13. AUTENTICACAO - escolha UM caminho para aprender primeiro
   Caminho 1 (mais simples): sessao + form login
     [ ] UserDetailsService carregando Usuario pelo email
     [ ] Spring cuida do login e da sessao (cookie JSESSIONID)
   Caminho 2 (mais comum em API + front separado): JWT
     [ ] UserDetailsService + AuthenticationManager
     [ ] POST /auth/login devolve o token
     [ ] Filtro (OncePerRequestFilter) que le o header Authorization: Bearer
     [ ] Sessao STATELESS
   PERGUNTE-SE: qual a diferenca pratica entre sessao e token para um
   front em outra origem (porta/dominio)? Qual voce quer entender primeiro?

14. AUTORIZACAO (opcional, se sobrar energia)
   [ ] Campo "role" simples (USER/ADMIN) como String ou enum (sem relacionamento)
   [ ] Restringir DELETE e listagem a ADMIN
   [ ] Testar 401 (nao autenticado) vs 403 (sem permissao)

FASE C - CONECTAR COM O FRONT (HTML, CSS, JS)
------------------------------------------------------------------------------

15. TELAS MINIMAS

   [ ] login.html (email, senha)
   [ ] Uma pagina protegida simples (ex.: perfil.html) para provar o login

16. JS PARA CONSUMIR A API
   [ ] fetch() com method POST, headers Content-Type: application/json e
       body JSON.stringify(...)
   [ ] async/await e tratamento de erro (response.ok, status 400/409/401)
   [ ] Mostrar na tela as mensagens de erro que o GlobalExceptionHandler devolve
   [ ] Se usar JWT: guardar o token e enviar no header Authorization
   PERGUNTE-SE: onde guardar o token (localStorage x cookie HttpOnly)?
   Quais os riscos de cada um?

17. CORS
   [ ] Se o front estiver em outra origem (ex.: Live Server na porta 5500),
       configurar CORS no Spring (CorsConfigurationSource no Security)

       src/main/resources/static e servir tudo pelo Spring (mesma origem)
   PERGUNTE-SE: o que e "origem" e por que o navegador bloqueia a chamada
   antes de a API sequer responder?
